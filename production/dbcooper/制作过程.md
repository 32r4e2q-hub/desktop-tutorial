# 《D.B. Cooper：雨夜里消失的名字》制作过程

三分钟横屏中文解说短片（1920×1080 / 30fps / 180s），由 `production/new_topic.py` 从参考项目
`production/dahlia/` 开出。本文记录**这一版为什么重做、重做了什么、坑在哪**——
成片与实测报告在 `delivery/` 与 `交付/`，流水线的通用做法在
[`新题目开工手册.md`](../../新题目开工手册.md)，这里只写本片特有的部分。

---

## 一、这一版是被两条意见逼出来的

上一版被打回的理由很具体：**「运镜总是从远到近飞入」「解说跟画面对不上」**。
这两条都不是"再渲染一遍就好"的问题，而是**计划阶段就没做**：

| 意见 | 根因 | 这一版的对策（都可核对） |
|---|---|---|
| 运镜单一 | `story.json` 没有"运镜"这个字段，提示词里只写"cinematic push-in" | 每镜一个 `camera` 字段：25 镜 **19 种**运镜，最多重复 2 次；提示词里写死 `Camera: …` 的具体动作；负向提示词禁 `fast zoom` / `whip pan` |
| 解说与画面不对应 | 剪辑表按"30 秒 5 刀 = 每 6 秒一刀"均匀切，切点落在句子里 | 先写解说稿，再按**真实配音上测出的自然停顿**定切点（`render.py` 的 `CUTS`，现 32 条 = 25 镜 + 6 卡 + S06/b + 复用之外的那一刀；无瑕疵轮把 S23 一张卡拆成两张时从 31 变 32），每镜 `purpose` 写明它承担哪句 |

这两条现在有测试钉住，不靠自觉：`production/tests/test_dbcooper.py`。
其中最硬的一条是**切点必须落在停顿上**——它解码已交付的 6 段配音，测出所有
≥0.14 秒的静音段，然后要求每个切点落在某个停顿的区间里（实测最大偏离 0.02 秒）。
把 `CUTS` 改回"每 6 秒一刀"，测试立刻红。

## 二、事实边界

- 5 条来源（FBI 官方页 / Britannica / Wikipedia / KIRO 7 / CBS News）写进 `story.json.sources`，
  每条标了它支撑哪几句解说；
- 全部 AI 画面标「AI情景重现 · 非历史影像」，手提箱/证物板/DNA 那几镜额外标注"静态道具 / 示意图 · 非原始证物图像"；
- **没有** 任何 `kind:"archive"` 镜头：劫机者没有可核实的真实照片，红线禁止用 AI 生成的脸冒充；
- 不指认任何嫌疑人——DNA 与指纹只陈述"比对后未得出名字"；
- 不渲染爆炸、伤亡；电线与红色火柴只作为打开箱子后的静态道具出现。

## 三、流水线上跑的东西（每步对应哪个文件）

```
剧本/分镜 → Agnes 生成 → 逐镜体检 → 配音 → 剪辑+字幕 → 混音 → 成片复测 → 审片/听检
story.json  generate.py   qa/Sxx.jpg  audio/   render.py   build_audio.py  render.py   review_film.py
                                     manifest.json                    delivery/*.json  + 人工看片
```

* 闸门一 `generate.py --validate`：180 秒时间轴、30 镜、每镜请求哈希、6 段配音的 SHA-256 与文字逐字一致；
* 闸门二 `build_audio.py`：整体 RMS / 峰值 / 波峰因数 / 静音占比 / **逐章**电平；
* 闸门三 `render.py` 收尾：对**最终 mp4** 再测一遍，不达标直接失败。

## 四、素材生成：跑在 Actions，不跑在沙箱

沙箱连不上 Agnes API（也连不上 CDN：`curl` 直接 000），所以生成必须发生在 runner 上。
`dbcooper-agnes.workflow.yml` → `.github/workflows/dbcooper-gen.yml`（逐字节，测试守着一致性），
它现在有**两条触发路径**：

* 人在 Actions 点「DB库珀 · Agnes生成」，填 `payload`；
* 代理把 `{"only":"S05,S10","workers":2}` 写进 `production/dbcooper/GEN_REQUEST` 再 push——
  **只有这个文件变化才触发**，因为生成器每完成一镜都会把 `results.json` 与 `qa/`
  commit 回本分支，paths 过滤器写宽了就是自我循环。

25 镜 × 75 秒节流（免费档 1 分钟 1 次创建）实测 57 分钟跑完 24 镜，逐镜 checkpoint
意味着中途断了不用重来：已完成的镜头按 `request_hash` + SHA-256 **复用 CDN 上的原文件**，
不重新消耗额度。

### 坑一：`--publish` 只认分支名

`generate.py` 里 `BRANCH` 是写死的，换分支必须同步改（`story.json['branch']`、
`watch_run.py`、工作流的 `if:` / `ref:` / `paths.branches` 四处）。
漏改任何一处的症状都是**"跑了但什么都没发生"**：job 被 `if` 静默跳过，或
`--publish` 抛错。`test_generation_workflow_still_points_at_this_branch` 就是防这个的。

### 坑二：provider 判死的任务，重跑修不好

S10 两次 `Video task failed: Generation failed: Fault failed: 2 (code=500)`。
断点续跑会拿着 `results.json` 里记住的 `task_id` 去**轮询同一个已经死掉的任务**——
于是无论重跑多少次都卡在原地。修法：`generate.py --prune-failed` 先把
"没有 `video_url` 的非 completed 记录"删掉（有 `video_url` 的保留，那种只是没下载完），
工作流在生成前固定跑一步。

**这一步本身也踩过坑**：第一版 `--prune-failed` 清完继续往下跑，
把"清理"步变成了第二次全量生成，补镜的失败还算在清理头上（出片那步根本没跑）。
现在它清完即退，有 `test_prune_flag_cleans_and_exits_without_generating` 钉住。

### 坑三：自动闸门看不见"该不该露脸""机型对不对"

24 镜生成完，逐镜看 `qa/Sxx.jpg` 打回了四镜：

| 镜头 | 问题 | 处理 |
|---|---|---|
| S05 空姐跟镜 | 人物转身面向镜头，正脸全程可见，与本片"机组不露正脸"冲突 | 提示词加硬：机位整段留在她背后，任何一帧不许出现人脸 |
| S11 盘旋航拍 | 内容是"盘旋的飞机"，模型自作主张切进驾驶舱与候机楼（多张正脸 + 内容漂移） | 提示词加硬：纯外景航拍，绝不进机舱 |
| S17 跳伞远景 | 出来一架**红色单发螺旋桨小飞机**——那不是三发 T 尾的波音 727 | 提示词点名机型并写明"绝不是螺旋桨小飞机" |
| S10 降落伞装运 | provider 500，判死两次 | `--prune-failed` 清掉死任务后重新提交 |

重跑后 S05 的成品镜头只取 0.12–3.85 秒这一段（`render.py` 的窗口规则），
恰好是"只有背影"的部分——窗口选择与提示词是一起设计的，不是各干各的。

## 五、剪辑：为什么 `CUTS` 长这样

`render.py` 的 `CUTS` 是**每章一串 (原始配音秒数, 镜头, 变体)**：

* 秒数来自那 6 段 mp3 的停顿测量（不是估计、不是平均）；
* 每章的 5–6 个切点只在本章的 5 个镜头里挑，跨章即测试红；
* `S06/b` 是唯一"回到同一素材"的复用：递纸条与打开纸条共用一镜的前后半段；
* 编辑窗口不整：最短 1.67 秒（S16 后舱门），最长 9.96 秒（S27 案件状态卡）。
  素材是 7.04 秒一镜，所以窗口超过素材可用时长时要做 ≤1.33 倍慢放——
  超闸门就报错，不用慢动作掩盖坏素材（`test_no_edit_window_is_too_long_to_fill` 把这条
  在**出片之前**就算出来，省一次 40 分钟的失败运行）。

信息卡只有 5 张，且只在解说说到那个数字时出现：S03（人物描述）、S08（二十万美元/四个降落伞）、
S20（NORJAK 与彻夜搜索）、S23（头五年 800 余名→只剩 24 名）、S27（至今未破）。
"卡面文字与本章解说同源"也是测试项——改解说稿忘了改卡，红的是测试而不是观众看到的错字。

## 六、配音

六段 `audio/N01–N06.mp3`，voice-00（用户试听两版后选定），`audio/manifest.json` 记文字与
SHA-256；渲染时逐字比对文本+哈希，防止"画面是这版、配音是上一版"。
六段实测时长 28.92 / 25.56 / 28.24 / 25.64 / 29.24 / 27.76 秒，合计 165.36 秒，
可用窗口 168.0 秒 → 全片变速 0.984（±14% 闸门内，不需要为了塞进 180 秒而挤压语速）。

## 七、出片与交付

* 出片：`bash production/run_project.sh dbcooper false DB库珀劫机案_三分钟_带声音.mp4`，
  或 Actions 的「解说短片出片」（`project=dbcooper`）；代理侧走
  `production/dbcooper/RENDER_REQUEST` 的 push（`.github/workflows/dbcooper-render.yml`）。
* 成片：`交付/DB库珀劫机案_三分钟_带声音.mp4`；报告：`production/dbcooper/delivery/`。
实测（`delivery/final-audio-report.json`，对最终 mp4 复测）：

```
容器：1920×1080 / 30fps / 5400 帧 / 180.0 秒 / h264 + AAC 48kHz 立体声 / 55,601,639 字节
混音：−21.75 dBFS RMS   峰值 −1.52   静音占比 0.56%
成片：−21.77 dBFS RMS   峰值 −1.50   静音占比 1.1%（只有 179–180s 淡出那一格低于 −50 dBFS）
逐章：N01 −21.67  N02 −21.39  N03 −21.50  N04 −21.45  N05 −21.58  N06 −21.32 dBFS
剪辑：34 个编辑段（25 镜 + 6 张数据卡 + S06/b + S14/b 复用 + 片尾卡），0 缝隙 0 重叠，变速比最大 1.308
对轨：5/6 章 ASR-assisted（匹配度 0.978–1.0），N02 回落停顿估算；166 个字幕边界逐一量过能量，
      全部落在语音低点或章首尾（boundary_penalty 0.0，见 delivery/alignment-report.json）
```

成片 SHA-256 `4bc53d9b5d84733e…`（52,907,291 字节，全长见 `technical-report.json`）。
本轮一共出了四版，依次替换：`6e110ff0…`→`25970170…`→`41cdd275…`→现版；
每一版替换的原因与逐条证据都写在 `review/审片与听检-2026-09-13.md` 第四节和
`delivery/review-summary.json` 的台账里。
* 审片：`production/review_film.py`（黑帧、冻结帧带 64×64 复核与 verdict、逐章电平、逐段语速）
  + 人工看 `contact-sheet-*.png`；
* 逐字听检：`.github/workflows/verbatim-check.yml` → `delivery/verbatim-check.json`
  （ASR 转写成片与剧本算 CER，刻意不给 `initial_prompt`，否则等于把答案先告诉模型）。

## 八、瑕疵台账：逐条要么消掉，要么写清为什么不消

判定口径来自用户那一句「要无瑕疵版本」：**凡是还能靠改提示词、改代码消除的缺陷都要消掉，
消除不了的必须留下证据和理由**。最终成片 `4bc53d9b…`（52,907,291 字节 / 33 段 / 5400 帧）上：

* **已修并在成片复验（9 条）**：S11、S13、S17、S28（机型与自拼字样）、S12（翼下短舱 → 尾视角）、
  S24（证物板上的铅笔男脸 → 整物删除，只留领带与空白卡）、S22（假钞面额与牛皮纸伪字 → 四抽，
  最后一抽让画面里不存在可被印刷的纸面）、S23（数据卡与台词各说一半 → 按 `variant` 拆两张，
  切点用真实开口秒）、字幕时间戳（两套对轨按实测能量择优 + 逐边界测试）；
* **判定不修并给理由（6 条）**：S07 只到肩颈（五官不可辨）；175 帧"接近全黑"（夜航、开舱门、
  台灯档案、片头尾淡变，实测 11.1–11.93，内容可辨）；38 处冻结嫌疑里的 11 真静止（6 张卡 +
  固定机位，本该静止）；「它再次起飞」压在登机镜尾巴上约 1.2 秒（挪它要重排整章时长）；
  S20 卡尾的 FBI 引语（卡面同向不矛盾，但不把无法逐字核对的引语做成档案件样式）；
  S13 两只袋子 vs S09 一只（谁都没说数量）；
* **`visual_review` 保持 `pending`**：自动闸门没跑逐帧人眼判定，报告就不替片子声称它没有的东西，
  人工判定逐条写在 `delivery/review-summary.json` 与 `review/` 里；
* 复验证据全部是**成片全帧**（15 个时间点 + 两处 1600px 裁放），不是接触印相——
  上一轮正是只看 4×4 印相才把 S12/S22/S24 判成"可接受"，这个教训写在
  `review/审片与听检-2026-09-13.md` 第四节。

流程上还留了一条硬约定：**一次 push 只碰一张便签**（`GEN_REQUEST` / `RENDER_REQUEST` /
`VERBATIM_REQUEST`）。`seq6` 那次同时 bump 两张，gen 的 checkpoint 先把分支推进，出片的裸 push
被 `fetch first` 拒掉——运行红、片子却是好的。现在共用脚本 `production/run_project.sh` 的发布步
会 `fetch + rebase` 重试三次，并由 `test_publish_step_survives_a_moved_branch` 钉住。

## 九、仍然存在的边界

* 人工看片是**全帧抽样**（每 5 秒 1 帧 + 关键镜头在 CUTS 窗口内取 3 帧），不是 5400 帧逐帧过；
  没看过的帧不在任何"已验"声称里；
* 逐字听检对最终成片重跑过（`delivery/verbatim-check.json`）：六章 CER 0.029–0.077、
  `failing: []`；报告现在自带 `film_sha256`，并由
  `DeliveryTests::test_listening_report_is_bound_to_the_delivered_film` 要求它等于
  `technical-report.json` 的 sha——之前它只记文件名，同一句"CER 全过"可以被任何一版成片沿用。
  本版往前数六个连续交付版本（`b10cad23`/`a8460c30`/`86f89636`/`200b3784`/`efe1f921`/`974a487f`）的 AAC 流
  sha256 前缀同为 `4976ca9100e9264e`——逐字节相同，所以 CER 逐章一模一样；这不是抄来的：
  配音是同一批 `audio/N0x.mp3`、混音是确定性的，
  但这句话只有在报告绑定指纹之后才可以说。
* 沙箱到不了 Agnes CDN 与 Hugging Face，所以"看片"依赖 Actions 把 `qa/` 与报告 commit 回来，
  成片本身也靠 git 取（Actions 的 artifact 在本环境下载不到）；ASR/解码类改动无法本地预验，
  只能在交付产物上量（ffmpeg + numpy）或交给 runner；
* GitHub 授权在这一轮里掉了两次（`gh` 与 `git` 同时 401，约每小时一次），第二次正好卡在
  `seq6` 出片的等待窗口里——流水线的设计（checkpoint + 按哈希复用）就是为这种中断准备的：
  重连后 `git fetch` 一看就知道差了什么，重跑一次 `RENDER_REQUEST` 即可，素材与配音都不用重做；

## 十、第四轮（同日）：把"内部便条"和"模型补完的属性"一起清掉

起点是两件一直没碰的小事，查完它们顺出了一整类问题。这一轮跑了 5 次生成、3 次出片、1 次听检，
台账 21 条 → **30 条**（已修并在成片复验 21 · 不修或残留并给量化理由 8 · 有意保留 1），成片版本链 7 → 10。

* **片尾卡印着 `story.json`**——那是给协作的人看的内部便条，不是给观众看的来源说明。改成
  `资料来源：FBI 案件页与四条公开报道 · 解说原创 · 画面为 AI 情景重现`，成片实测墨迹跨度 x624–1298（面板内、未顶边）；
  `render.py` 里所有 `centered(` / `d.text(` 的字面量从此由测试扫描。
* **`archive_image()` 里留着参考项目的三行「TODO 档案卡标题」**。本片 archive 镜头数为 0，它没上过屏，
  但"没人点到它"不是闸门。现在它 `raise RuntimeError`，测试直接调用它断言抛异常。
* **加测试时自己踩到一个静默空跑**：那段用 `story.get('narration', [])`，而 `story.json` 的顶层键是
  `chapters` ——默认值让断言对着空列表跑，测试"绿"得毫无内容。改成 `story['chapters']` 才是真在测。
  凡是"从产物里取一份清单再断言"的测试，都要先确认那份清单不是空的。
* **S28 机头两组红色字母状图形**（约 55×75 px/处，1080p 下读得出"是字"），而提示词里
  `no letters of any kind` 写了两遍。第 5 抽把飞机推到机坪尽头，成片机身框内偏红像素首/中/末三点均为 0
  （旧版同框 2 处），机身横向跨度 266→300 px（放大比 1.128，"距离恒定"这次被执行）。
* **躲文字时我把机型写坏了**：`twin-jet + engines slung under the wings` 是 737/DC-9，不是本片的三发 727。
  新测试 `PlanTests::test_the_airframe_is_the_same_aircraft_in_every_shot_that_shows_it` 从此钉住：
  凡机身入画必须声明 727/三发并否定翼下吊发，镜头集合钉死为 S11/S12/S13/S28，多一个少一个都要人来解释；
  "画面里根本没有飞机"算另一种正解，所以 S10/S17 不在集合内。
* 这条测试立刻抓到两处旧账：**S01** 开场那颗翼下短舱 85×46 px 且合焦（片名就压在旁边）、**S10** 顶边 40×30 px 虚焦。
  S01 为此连抽三次——第 5 抽消掉短舱却刷出一条伪航司字（印相里几乎读成 …COOPER…）且机位变绕机；
  第 6 抽消掉字却画出一架不存在的混合机（正面 T-tail + 三具翼下短舱）；
  第 7 抽索性把飞机从命题里取消：开场只剩航站楼玻璃立面、两座廊桥、湿机坪与一排年代感轿车，
  立面带强边缘像素占比 0.18–0.25%、最大"告示牌"27×12 px 无可辨字形，机位回到与 camera 标签一致的匀速横移。
* **四张档案卡的表头** `PACIFIC NORTHWEST · 1971` 改成 `PORTLAND-SEATTLE-RENO · 1971`：
