# 制作过程 · 《李春才：华城连环杀人案，DNA揭开了33年的秘密》

照 [`新题目开工手册.md`](../../新题目开工手册.md)（狂犬病模式）做的第五部片子，
第四部露脸模式的片子（前三部是《雨夜屠夫林过云》《韩国雨衣杀手柳永哲》《日本座间九人案》）。
用户指定按 **`zama2017-v1`（座间九人案）模板**制作，并提了四条硬要求：
**3D 动画视频（不是图片视频）、人物鲜活（不同人物不同脸、同一人物同一张脸）、
动作幅度大（中景/全景 + 明确动作 + 运动镜头，不要人脸特写糊弄）、内容丰富饱满**。

分支：`arena/3c6cd684-desktop-tutorial`　项目：`production/hwaseong1986`
成片目标：180 秒 / 1920×1080 / 30 fps / 45 镜（38 Agnes + 7 信息卡）。

## 4. 露脸模式（本片重点）

- 五个虚构匿名角色：**C1 年轻男子（李春才 · 一九八六至一九九四年情景）**、**C2 年轻男子（尹成汝 · 一九八八年）**、
  **C3 老刑警（调查本部长）**、**C4 重查组警官（二〇一九年）**、**C5 女法医（DNA 检测）**。
  `cast.json` 里每人一条面容 token（≥60 字）、一个固定 seed、一张定妆照。
  **不做任何真实人物的肖像还原**——李春才在二〇一九年后的镜头只给背影。
- 同一张脸跨镜稳定靠三件事叠加（与座间/林过云同一套接线，`generate.py` 的 `cast_ledger` /
  `shot_seed` 从座间版逐字移植）：
  1. 提示词里**逐字节**照抄该角色的 face token（`{C1}`…`{C5}` 占位符从 `cast.json` 注入）；
  2. 单角色镜头用**角色 seed**（C1=19860915 首案日 / C2=19880916 第八案日 / C3=19861212 /
     C4=20190919 DNA 突破日 / C5=20190801 比对月）；
  3. 五个角色的**首次露脸镜头（S06 / S12 / S16 / S27 / S40）用定妆照做图生视频首帧**。
- 动作幅度：`STYLE_PREFIX` 明确要求 `full-body movement and expressive gesture, staged in medium
  and wide shots rather than close-ups`；分镜里 9 个露脸镜头有 6 个是全身/中景动作镜
  （夜路行走、地图墙撑墙、公交站被拦、法庭被告席、审讯低头、讲台发言），
  只有 S06 / S27 / S40 是偏近的镜位，且都有明确动作（望窗、对报告、举证物）。

## 9. 卡住的真正原因：供应商侧「模型没有可用通道」（2026-10-10）

第 8 节提交 `GEN_REQUEST` 之后，生成一步没有往前走。**0/38 镜**，连续 6 轮 Actions 全红。

### 证据（都来自分支上的 `results.json` 与 `gh run list`）

- 供应商返回的原文（`results.json` 的 `shots.S03.error`）：
  `HTTP 503: No available channel for model agnes-video-v2.0 under group default (distributor)`
  —— 网关（`apihub.agnes-ai.com`）在说「这个模型当前一个可用通道都没有」，不是我们的请求写错了。
- 时间线：`2026-10-10T00:30Z` 起持续（00:30 / 01:19 / 01:37 / 04:31 / 04:42 / 04:55 六轮），
  到 05:37Z 仍在报同一个错；而同一把 key、同一个模型 **2026-10-09T11:57Z 还成功出过片**
  （杰克·翁特维格，run 37926988045）。所以不是 key 失效，也不是提示词问题。
- 期间还夹了一个**我们自己的 bug**：`push_provenance` 被误缩进嵌进了 `checkpoint` 里面，
  第一次调用就 `UnboundLocalError`，两轮运行在 1~2 分钟内就死（run 38024372451 / 38025010111）。
  已在 `821b56a` 修好；但 `results.json` 里那条 `pipeline_error` 是**上一轮**留下的，
  新一轮启动时没清掉，于是修好之后看起来像又复发了一次。

### 处理（本分支）

| 改动 | 为什么 |
|---|---|
| `generate.py`：新增 `ProviderCapacity` 异常 + `ChannelBreaker` 共享熔断 | 旧策略把 503 当普通退避：每镜试 8 次、每次冷却最长 300 秒 → **每镜烧掉约 50 分钟**才失败，一整轮跑满 3 小时（run 38013901390）一个素材都没有 |
| 连续 `channel_error_limit`（默认 3）轮通道不可用 → 整轮立刻停，`phase=provider_capacity` | 「供应商没通道」和「流水线自己有 bug」必须分开，否则下一个人会去改根本没有坏的代码 |
| `wait_channel_minutes` 等待预算（本轮 120 分钟） | 想扛过波动就给预算：冷却期只等、不创建任务、不占额度；预算用尽才放弃 |
| `generate()` 里 `except ProviderCapacity: raise` | 不加这句，整轮异常会被单镜的 `except Exception` 吞掉，phase 变成 `generation_incomplete`，看起来像素材没做完 |
| 启动时 `doc.pop('pipeline_error')` / `doc.pop('provider_outage')` | 旧错误留在 results.json 里会误导诊断（这次就被误导了一回） |
| 新增 `probe_provider()` → `delivery/provider-probe.json` | 沙箱连不上 Agnes、也读不到 Actions 日志；开跑前/放弃前各量一次 `GET /v1/models`（不创建任务、不花额度），把「到底谁的问题」变成仓库里的一张收据 |
| 新增 `production/tests/test_provider_capacity.py`（8 个用例，离线） | 这段逻辑跑在 runner 上要几十分钟才看得出结果；现在 `pytest production/tests -q` 就能跑一遍：整轮只发 3 次创建请求（不是 38×8 次）、phase 正确、旧错误被清掉 |

### 什么时候能继续

通道恢复后重投一次即可，已完成的镜头按 SHA-256 复用、不会重复消耗额度：

```bash
# 改一下 GEN_REQUEST 再 push，或在 Actions 里 workflow_dispatch 填 payload
{"workers": 2, "wait_channel_minutes": 120}
```

要判断通道回没回来，看 `delivery/provider-probe.json` 的 `target_model_listed`；
仍然 `false` 就说明是供应商侧还没恢复，继续重投只是白烧 runner 时间。

## 10. 真正的原因：`agnes-video-v2.0` 被供应商下线了（2026-10-10T06:03Z 探针实测）

第 9 节加的网关探针第一次跑就给出了答案。`delivery/provider-probe.json`：

```json
{"model": "agnes-video-v2.0", "http_status": 200, "target_model_listed": false,
 "models": ["agnes-2.5-pro-alpha", "agnes-video-2.5-flash", "agnes-3.0-flash",
            "agnes-image-2.1-flash", "agnes-video-2.5", "agnes-2.0-flash",
            "agnes-image-2.0-flash", "agnes-2.5-flash", "agnes-3.0-flash-max",
            "agnes-2.5-pro", "agnes-2.5-pro-beta", "agnes-image-2.5-flash"]}
```

网关（`apihub.agnes-ai.com`）的模型清单里**已经没有 `agnes-video-v2.0`**，视频模型只剩
`agnes-video-2.5` 与 `agnes-video-2.5-flash`。所以那句 503 不是「通道波动」，是**模型被下线**——
等多久都不会回来，前面 5 个小时、6 轮重投全都是白烧。

（这也解释了时间线：2026-10-09T11:57Z 还能出片，10-10T00:30Z 起就再也没成功过。）

### 处理

| 改动 | 说明 |
|---|---|
| `generate.py`：新增 `MODEL`（默认 `agnes-video-2.5`，`AGNES_VIDEO_MODEL` 或 payload 的 `model` 可覆盖） | 创建、轮询、探针、收据、交付说明全部跟着它走 |
| `validate()` 的模型断言跟着 `MODEL` | 原来写死 `agnes-video-v2.0`，不改就是自己拦自己 |
| `render.py` 的模型闸门改成 `from generate import MODEL` | 原来写死旧名字，换模型后**所有素材都会被拒绝出片**，而且报的是「Only the requested Agnes model is allowed」，看不出是模型换代 |
| `results.json` 启动时强制写 `doc['model']=MODEL` | 旧文件里留着旧模型名，同样会撞上上面那道闸门 |
| `script_table.py` 的脚本抬头改用 `MODEL`，重新生成 `抖音脚本.md` | 发布物料里不能再写「Agnes Video V2.0」 |
| `production/agnes_video.py` 的 `DEFAULT_MODEL` **没有动** | 它是所有项目共用的实现；本片按项目覆盖，别的项目要换各自决定 |

## 11. 最后一道墙：账号余额 ＄0.000000（2026-10-10T07:00Z 实测）

payload 按文档改对之后，创建请求**越过了字段校验**，撞上新的一道：

```
HTTP 403: Insufficient user quota, remaining: ＄0.000000
(request id: 20261010065941375220354tcOnQaCa)
```

这不是代码问题，是 Agnes 账号里没钱了。到此为止，**流水线本身已经没有已知障碍**：
选题/解说/分镜/配音/闸门/剪辑表/冒烟测试早就绿了，模型与 payload 也对了，
只差供应商那边有额度。

### 现在必须人来做的两件事之一

1. 给 `AGNES_API_KEY` 对应的账号充值（平台：https://platform.agnes-ai.com/settings/apiKeys ）；
2. 或者换一把有额度的 key（仓库 secret `AGNES_API_KEY`）。

预算参考（文档价目：720P $0.025/秒、1080P $0.040/秒，前 5 张输入图免费）：

| 档位 | 38 镜 × 7 秒 = 266 秒 | 备注 |
|---|---|---|
| 1080P（当前 `SIZE_TIER`） | ≈ **$10.64** | 成片 1920×1080，不用放大 |
| 720P | ≈ $6.65 | 渲染时放大到 1080P，画质略软 |

### 顺手补的防呆

`generate.py` 新增 `QuotaExhausted`：认得「Insufficient user quota」这类文案就
**一次请求即停整轮**（`phase=quota_exhausted`），不再让 38 个镜头各撞一次 403、
把一整轮 runner 时间烧光。普通 403（key 写错）不会被误判成「去充值」。
离线用例：`production/tests/test_provider_capacity.py`（`pytest production/tests -q`：137 passed）。

### 充好值之后怎么接着跑

```bash
# 改一下 production/hwaseong1986/GEN_REQUEST 再 push 即可（断点续跑，已完成镜头按 SHA-256 复用）
{"workers": 2, "wait_channel_minutes": 120}
```

## 12. 定型：免费方案 = `agnes-video-2.5-flash` + 720P（2026-10-10T08:0xZ）

用户拍板走免费方案。三档实测（收据都在 `delivery/provider-probe.json` 与 `results.json`）：

| 组合 | 结果 | 结论 |
|---|---|---|
| `agnes-video-2.5` + 1080P | `403 Insufficient user quota, remaining: ＄0.000000` | 主档要余额，两把 key 都是 $0 |
| `agnes-video-2.5-flash` + 1080P | `400 size must be one of 720P` | flash 只有 720P 档 |
| `agnes-video-2.5-flash` + **720P** | `503 video queue is full, please retry later` | ✅ **过了额度闸门**，只剩排队 |

代价：720P 素材由 `render.py` 放大到 1920×1080 出片，画面比原生 1080P 略软。

### 顺手修掉的一个隐患：模型名两边不一致

`render.py` 的出片闸门原本写死模型名，而生成时模型可以被 payload/env 覆盖 ——
两边一旦不一致，**38 个素材全生成完了才会发现整片被拒**，报的还是看不懂的
「Only the requested Agnes model is allowed」。

修法不是把默认值改成一致就完事，而是新开 `model_policy.py` 作为唯一出处：

- `render.py` 里 `from generate import ...` 会**撞到别的项目的 generate.py**
  （仓库里每个项目都有一个；实测 `ImportError: cannot import name 'MODEL' from 'generate'
  → production/dahlia/generate.py`，连带把 `test_card_typography.py` 也弄红）；
- `render.py` 是 `generate.py` 用 subprocess 起的**另一个进程**，跨进程共享一个
  「运行时会被覆盖的变量」本来就不成立。

`model_policy.py` 提供 `MODEL` / `SIZE_TIER` / `ALLOWED_MODELS`（出片闸门认的白名单）/
`SUPPORTED_SIZES` / `SUPPORTED_MODES`；测试断言「生成产出的模型一定在白名单里」。

## 13. 第一个镜头出片了：排队是「抽签」，不是「堵车」（2026-10-10T09:22Z 实测）

**S03 建成了**，这是整条链路上第一段真正的 AI 画面。`qa/S03.json` 的实测数据：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 分辨率 | **1280×720** | 免费档只给 720P，出片时由 `render.py` 放大到 1920×1080 |
| 时长 | 7.328 s（175 帧 @ **24 fps**） | 要 7 秒给 7.33 秒，够用；24 fps 会在出片时补到 30 fps |
| 体积 / 编码 | 2 317 486 字节，h264 + aac | `decoded_ok: true` |
| 排队→出片 | 09:11:30 提交 → 09:22:49 完成，**约 11 分钟** | 排队时间主要花在「能不能提交」，不在生成 |
| 声音 | 模型自带环境声 | 出片时整轨替换为解说+配乐，不会被用上 |

**关键发现：`video queue is full` 不是「队伍很长」，而是「每次请求都在抽签」。**
从 08:11 到 10:02 一共 23 次创建尝试，只成功 1 次；中间 08:41 / 08:51 / 09:01 三次连着被拒，
09:11 那次就过了。所以吞吐量的决定因素是**每小时能抽多少次签**，而不是等多久。

原来的退避是 300 秒一档（那是给「模型下线」设计的），等于每小时只抽 12 次签 ——
38 个镜头按 1/23 的成功率要排到下周。这一节改了三件事：

1. **两种 503 分开对待。** `no available channel`（模型真的没通道）仍然 300 秒长冷却，
   等再久也不会变好；`video queue is full` 缩到 **90 秒**（仍在免费额度 1 次/分钟之内），
   抽签次数从 12 次/小时提到 40 次/小时。`capacity_problem()` 现在返回 `(原因, 冷却秒数)`。
2. **等待预算改成「多久没进展」。** 原来 `ChannelBreaker.started` 是开跑时刻，
   140 分钟一到、再连败两轮就整轮放弃 —— 而 S03 明明 09:11 才刚出片。
   现在 `note_success()` 会把等待时钟一起清零：只要还在出素材就一直跑，
   连续 140 分钟一个都没成才收工。
3. **排队没排到就自动再投一轮。** 工作流最后加了一步：`phase=provider_capacity` 时
   把 `GEN_REQUEST` 的 `round` +1 推回去，自动开下一轮接着没做完的镜头跑（上限 12 轮，
   免得欠费/下线这类真故障无限烧 runner）。每个镜头的断点带 SHA-256，
   已生成的素材会被复用，不会重花一分钱。
