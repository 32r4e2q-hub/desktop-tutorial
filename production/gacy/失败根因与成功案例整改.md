# 失败根因与成功案例整改（2026-10-24）

## 一、先核实是否真的“一个视频也没有”

- GitHub Issue #44 是真实的成功日志，不是仅凭工作流绿色判断：默认小松鼠提示，任务 `20261024101554a7aa2599cbe04555`，67秒后SUCCESS，下载2,957,309字节。
- 只读恢复运行40064335411再次查询该ID并下载，FFprobe核实1792×1024、5.108108秒、SHA-256 `92df6e9f48ff65ab52b437b9b647024c123c35ed7a208ac5bd2bbbdadc64b990`。
- **它不是盖西影片素材，不能拿来凑成片。** 此片正式镜头目前仍没有已验证下载。
- 本片带图实验C1-A的已有任务在恢复查询中返回FAIL，已经不是PROCESSING。初次十分钟等待结束时只有“仍未完成”的证据；本轮才确认其最终失败。具体服务端失败码必须进一步记录，不能猜测为限流、审核或参数不支持。

## 二、实际存在的故障分层

1. 提交429/1305：服务端明确容量拒绝，根本没有任务ID。可有界退避，不应当成成功排队。
2. 查询400/1301：旧视觉修订被服务端审核拒绝。属于永久性审核结果；不重投相同修订，不编码/隐藏内容绕过。
3. 已受理后仍PROCESSING：只代表排队/执行中。等待窗到期不等于生成失败，也不能重新提交制造重复任务。
4. 查询返回FAIL：此任务已终止。必须保存服务端错误详情；只允许已确认的瞬时执行故障1234进入有限新任务替换，先归档旧收据。未知错误与审核结果不自动替换。
5. SUCCESS却没文件：生成成功和下载/媒体验证要分开记；先验证HTTP与FFprobe，不能仅因URL存在就计数成功。

## 三、原实现的问题（承担责任）

- 同脸实验只给600秒查询窗，短于参考项目120次×10秒的约20分钟轮询窗。
- 超时只有通用RuntimeError，冷却器仅捕捉ProviderError；所以任务已受理后超时直接穿透，根本没有续查。
- 异常退出时retry-status.json仍可能保留running，造成“自动三轮还在跑”的误解。
- 未持久化每次正常查询的PROCESSING/SUCCESS/FAIL，只存了请求异常，无法知道最后处于哪个阶段。
- 查询FAIL时丢弃了服务端error.code/message，难以与审核、网络故障区分。
- 没有按玛丽号案例接上42退出码、Actions自派发与完整的轮次上限；保存任务ID不等于有程序会自动续查。
- 之前说“一个视频都没有”范围不严谨：成功的连通性对照确实存在，但不属于本片。

## 四、对照仓库成功案例的修复

参考 `arena/63ceeca2-desktop-tutorial` 的 `production/maryceleste1872/generate_cogvideox.py`、`auto_resume.py` 和《制作过程》§6/§10：

- 统一官方SDK调用；制作路线免费CogVideoX三字段，身份实验明确额外带image_url，不混淆两种模式。
- 新增VideoPendingError：保存原ID和最后状态，20分钟窗后只允许续查原任务，不新建重复任务。
- 正常查询也回存UTC、最后状态和次数；未知状态立即报告schema问题，不空转到超时。
- 新增VideoTaskFailedError，保留安全的错误码/说明；审核与未知失败硬停，1234终止网络故障归档后才允许有限替换。
- 冷却器现在接住Pending并在下一轮继续相同ID；所有错误分支都写终态，不留running。
- 主程序遇到确定的容量/执行瞬态或等待原任务，写awaiting_provider/provider_transient并返回42；真实错误仍非零，审核/鉴权/参数错误不接力。
- 工作流用set +e正确捕获PIPESTATUS，然后再决定是否接力，避免bash -e吞掉退出码。
- 新增relay.py，单个请求链最多3个工作流轮次并有零进展上限，重跑不重复计数；只是保存marker不算接力。
- 工作流显式actions:write，收据/缓存落盘后使用官方workflow_dispatch自派发。GITHUB_TOKEN推送不触发push，这是玛丽号手册明确记录的坑。若派发失败，工作流真实失败，不能声称下一轮已启动。
- 绿色仅表示该阶段处理/接力请求结束；step summary与run-status明确区分等待、恢复检查、同脸待审、成片待审。不将绿色等同于出片。
- 同脸审查未通过仍禁止正式合成，不以小松鼠对照、静态图片或未经检查的人脸替代交付。
